# План портирования AutPlay на macOS

Статус: исполнение начато по заданию пользователя. Дата: 13 октября 2026 года.

[Ход исполнения и проверки](../../operations/MACOS_PORT_STATUS.md). Исходный снимок:
`102380418421f87679732406f8052150e8226da8`, ветка `codex/macos-port-20261013`.

Цель — выпустить самостоятельный AutPlay для macOS с локальной библиотекой и воспроизведением без сервера, затем подключить существующие аккаунты, Vault и синхронизацию. Основной путь — Kotlin Multiplatform и Compose Multiplatform Desktop на JVM с отдельными адаптерами операционной системы.

Это технический план одного направления. Общие приоритеты и правила выпуска остаются в [плане готовности продукта](../../operations/PRODUCTION_READINESS_PLAN.md). Реализация начинается по отдельному заданию пользователя.

## Исходное состояние

- Gradle подключает только `:apps:android`. Общих клиентских модулей и desktop entry point пока нет.
- Интерфейс использует Jetpack Compose; воспроизведение и загрузки — Media3, локальная база — Room 3 с `BundledSQLiteDriver`, отложенные задачи — WorkManager.
- В текущем дереве база имеет версию 18. Есть незакоммиченные изменения приложения и сервера, включая переносимые аккаунты. Исходной точкой нельзя автоматически считать только текущий Git HEAD или старый релиз.
- Часть бизнес-логики и состояния плеера отделена от Android. Другие application-классы непосредственно используют базу, Android API или Media3 и требуют разделения зависимостей.
- Сервер требует небольшого по охвату, но существенного изменения совместимости устройств: контракт enrollment содержит `platform = ANDROID`, HTTP-валидатор и admission CHECK также ограничены Android. Portable account enrollment создаёт устройство с жёстко заданной платформой Android. Существующий enum устройств допускает `ANDROID`, `WEB`, `OTHER`.
- Все текущие CI jobs используют Linux. Установочный пакет и системные интеграции macOS требуют отдельного macOS-контура проверки.

## Границы первой версии

Основная платформа прототипа — Apple Silicon. Intel включается в отдельную сборку и матрицу проверки до заявления о поддержке Intel. Минимальную версию macOS определить на этапе проверки зависимостей и зафиксировать вместе с поддерживаемыми архитектурами.

| Возможность | Первый локальный прототип | Версия для ежедневного использования | Релиз |
| --- | --- | --- | --- |
| Импорт файлов, воспроизведение, перемотка, очередь | Да | Да | Да |
| Постоянная библиотека, поиск, плейлисты, история | Минимальный набор | Да | Да |
| Светлая и тёмная темы, русский и английский | Базовое оформление | Да | Да |
| Подключение сервера, аккаунт, Vault streaming | Проверка транспорта | Да | Да |
| Восстановление аккаунта, синхронизация данных | Нет | Основные сценарии | Полная проверка |
| Управляемые загрузки и офлайн-кеш | Нет | Следующий этап | Да |
| Медиаклавиши, системная информация о треке, sleep/wake | Нет | Базовая интеграция | Полная проверка |
| Остальные актуальные функции Android | Инвентаризация | По матрице функций | Закрыть согласованный объём |
| Установщик, подпись, нотариальное заверение | Тестовая упаковка | Тестовая сборка | Да |

На этапе 0 составить полную матрицу функций по текущему приложению: My Wave/рекомендации, Wave Rooms и guest-сценарии, социальные функции, редактирование тегов и обложек, импорт/экспорт, upload/download, поиск музыки, согласия и управление устройствами. Для каждой функции указать «входит в первый релиз» либо явный перенос в следующую версию. До закрытия матрицы не называть релиз полным функциональным паритетом.

AutPlay Face исключён из действующего продукта и не возвращается при переносе. Существующий сервер используется как удалённый сервис; установка сервера на Mac, перенос GPU-обработки, iOS и выпуск desktop для Windows/Linux — отдельные задачи. Desktop-клиент самостоятельно работает с локальной музыкой.

## Архитектура клиента

Предлагаемая структура модулей:

```text
shared/domain        models, identifiers, library and queue policies
shared/application   use cases, presentation states, platform ports
shared/data          Room entities, DAOs, migrations, repositories
shared/jvm           shared JVM transport, canonical JSON and crypto helpers
shared/ui            reusable Compose components and resources
apps/android         Activity, Media3, SAF, Keystore, WorkManager adapters
apps/desktop         desktop entry point, window shell, macOS adapters
```

В `commonMain` переносить только код без Android и Java API. Существующие Java crypto, OkHttp и RFC 8785 helpers можно переиспользовать для Android и desktop через общий JVM-модуль. Не переписывать проверенную криптографию ради формального размещения всего кода в `commonMain`.

Определить небольшие платформенные порты: воспроизведение, разрешение источника аудио, выбор/чтение файлов, секреты и подписи устройства, пути приложения, фоновые задачи, монотонные часы, системное управление плеером. Конкретные имена и сигнатуры зафиксировать в начале работы.

UI отображает состояние и отправляет команды. Очередь, библиотека, загрузки и история имеют по одному владельцу состояния. Android сохраняет Media3 и WorkManager как владельцев своих соответствующих операций; desktop получает собственные реализации этих границ.

## Этап 0 Подготовить исходную точку и рабочие границы

Ориентир: 1 рабочий день. Владелец: координатор.

1. Согласовать точную исходную версию приложения и сервера, включая нужные незакоммиченные файлы. Сохранить воспроизводимый снимок исходников с идентификатором и хешами; не сбрасывать чужие изменения.
2. Записать действующую схему БД, версии контрактов, поддерживаемые форматы аудио и матрицу пользовательских функций.
3. Подготовить доступный Mac или macOS CI. Отдельно определить наличие ARM64 и x64 проверки.
4. Проверить совместимость закреплённых Kotlin, Gradle, AGP, Room и новой Compose Multiplatform зависимости. Существующие версии сохранять; необходимые изменения toolchain выделить в отдельную проверяемую задачу.
5. Зафиксировать границы модулей, владельцев файлов и API платформенных портов. Расширение принятых решений по media ownership и device platform оформить отдельным ADR перед изменением соответствующего поведения.
6. Выполнить исходные затронутые Android/contract проверки и записать уже существующие сбои отдельно от результатов переноса.

Готовность: все рабочие чаты используют один снимок; известны целевые Mac, объём первого релиза и владельцы интерфейсов. Рабочие копии не теряют текущие изменения.

## Этап 1 Проверить аудио и нативные зависимости

Ориентир: 2–3 рабочих дня. Владелец: направление аудио и macOS. Начать сразу после подготовки снимка, параллельно с выделением общего кода.

Сравнить два варианта: AVFoundation через небольшой нативный мост и стабильный LibVLC/JVM binding. Выбор сделать по реальной проверке форматов, HTTP-авторизации/Range, точности seek, времени старта, потоковой модели, упаковке и лицензиям. Не привязывать продукт к движку до проверки этих сценариев.

Проверить MP3, AAC/M4A, FLAC, Opus и PCM WAV, локальный файл и поток с одноразового тестового сервера. Включить перемотку в начало/середину/конец, следующий/предыдущий трек, паузу, смену источника, обрыв сети и отмену загрузки. Использовать собственные или синтетические тестовые файлы.

Отдельно проверить доступ к Keychain и путь реализации подписей устройства на выбранном JVM/native стеке. Собрать минимальный `.app` и тестовый `.dmg`, чтобы ранняя проверка охватывала загружаемые нативные библиотеки, а не только запуск из IDE.

Для LibVLC проверить стабильную ветку binding и её совместимость с JDK проекта; текущая development-ветка vlcj ориентируется на VLC 4 и не должна автоматически становиться production-зависимостью. [Первичный источник vlcj](https://github.com/caprica/vlcj).

Готовность: выбранный движок проходит обязательную матрицу форматов и transport-сценариев на Mac; известны ограничения, лицензии, состав пакета и схема нативного моста. Если кандидат не проходит, заменить его на этом этапе и пересчитать зависимые задачи.

## Этап 2 Выделить общий код и адаптировать хранение

Ориентир: 3–5 рабочих дней. Владелец: направление общего кода и данных.

1. Добавить shared-модули и минимальный desktop entry point. Переносить код небольшими участками, сохраняя работающую Android-сборку после каждого участка.
2. Перенести модели, правила библиотеки, очередь, presentation state и действительно общие use cases. Отделить непосредственные вызовы Android API от логики принятия решений.
3. Выделить Room entities/DAOs и проверенные миграции. Открытие базы и файловые пути сделать платформенными; desktop хранит данные в `~/Library/Application Support/AutPlay`.
4. Разделить идентичность трека и локатор файла. Android `content://` остаётся Android-локатором; Mac хранит свой путь/закладку через собственный адаптер. Не записывать desktop-путь в поле, контракт которого требует реальный Android content URI.
5. Проверить FTS, SQL, транзакции, незавершённые операции и восстановление базы на desktop SQLite. Исторические Android схемы и миграционные fixtures сохранить.
6. Перенести JVM transport, канонизацию и пригодные crypto helpers. Зафиксировать одинаковые wire bytes, hashes и правила подписи на общей матрице fixtures.

Готовность: Android проходит затронутые проверки; desktop открывает постоянную базу, сохраняет библиотеку и очередь после перезапуска; общие правила проверяются без Android runtime. Room поддерживает JVM desktop, но корректность конкретных SQL и миграций AutPlay подтверждается собственными проверками. [Документация Room](https://developer.android.com/kotlin/multiplatform/room).

## Этап 3 Собрать локальный desktop плеер

Ориентир: 3–5 рабочих дней, параллельно с этапом 2 после фиксации портов. Владельцы: направления UI и аудио.

1. Сделать desktop shell: окно, навигация, библиотека, поиск, мини-плеер, экран трека и очередь. Переиспользовать пригодные Compose-компоненты; Android-зависимые оболочки оставить платформенными.
2. Перенести ресурсы EN/RU, цвета, темы и обложки. Добавить resize, focus, Tab-навигацию, клавиатурные действия и управление мышью.
3. Реализовать импорт выбранных файлов и папок, затем drag-and-drop. Явно закрепить политику: импорт создаёт управляемую проверенную копию, исходник сохраняется; отмена и повторный импорт не создают потерянные записи или дубликаты.
4. Сделать bounded сканирование/чтение метаданных вне UI потока. Проверить Unicode, длинные имена, одинаковые файлы, недоступные внешние диски и перемещение исходников.
5. Подключить настоящий движок к общему playback state. Сохранить duplicate queue entries, shuffle/repeat, историю прослушивания и стабильные ID сессий.
6. Сохранять playback checkpoint с теми же гарантиями, что и Android: периодически и на pause/seek/error/teardown. Перезапуск восстанавливает очередь и позицию без двойного события истории; автозапуск звука следует явной политике.

Готовность: без аккаунта и сети пользователь импортирует музыку, слушает её, меняет очередь, создаёт плейлист и после перезапуска получает сохранённую библиотеку и состояние. Это первый самостоятельный продуктовый результат.

## Этап 4 Расширить совместимость серверных устройств

Ориентир: 3–5 рабочих дней; возможно параллельно с локальным плеером. Владелец: координатор, затем направление данных.

1. Инвентаризировать enrollment/admission, portable accounts, pairing, self-pairing, recovery, deletion, device lists и server model CHECKs. Учесть Android-фильтры списков устройств, которые сейчас показывают только `ANDROID`.
2. Ввести явное обозначение `MACOS` через совместимое версионированное расширение запросов/схем и discovery capability. Точный способ версионирования определить в ADR; действующие Android v1 запросы должны продолжать работать.
3. Сохранить исходные signed payloads, nonce/idempotency и hash fixtures старых контрактов. Расширение платформы не ослабляет proof-of-possession, object authorization, ограничения запроса и процедуры доверия серверу.
4. Добавить недеструктивную миграцию серверных CHECKs и propagation платформы в создаваемые device records. Проверить на одноразовой БД со старыми Android-строками и новыми Mac-строками.
5. Проверить старый Android с обновлённым сервером; старый сервер с Mac должен возвращать понятную несовместимость. Mac не должен представляться Android для обхода ограничений.
6. Проверить корректное отображение и отзыв Mac-устройства в Admin и клиентских device lists, включая сохранение неизвестных будущих platform values.

Готовность: сервер отличает Mac от Android, старые Android-клиенты продолжают работать, подписи и миграции проверены. Изменения применяются к постоянному серверу только через существующую процедуру выпуска и развёртывания.

## Этап 5 Подключить аккаунт и Vault

Ориентир: 4–7 рабочих дней. Начинается после общего хранения, защищённого credential adapter и совместимых серверных контрактов.

1. Реализовать хранение секретов через Keychain и device signer. Не смешивать переносимую корневую идентичность аккаунта с новым ключом и ID конкретного Mac-устройства.
2. Подключить создание/вход, явное подключение устройства, recovery import/export, отключение сервера и восстановление после незавершённой операции. Для QR предусмотреть импорт изображения или кода; камера — отдельная возможность матрицы.
3. Проверить Android → Mac и Mac → Android на одних account/recovery fixtures, включая ошибочный пароль, повреждённый документ, подпись, ротацию и повтор после сетевого сбоя.
4. Перенести sync coordinator и atomic mutation + Journal/outbox transactions. Desktop scheduler хранит durable intent и восстанавливается после crash/sleep; процесс приложения не обещает выполнять задачи после полного завершения приложения.
5. Подключить Vault streaming с runtime-авторизацией, ограниченными retry/timeouts и проверенной redirect policy. URL и токены не сохраняются в очереди.
6. Проверить историю, предпочтения, плейлисты и статистику между двумя устройствами, offline изменения, повторную доставку, конфликт и смену аккаунта/сервера.
7. Аудиофайлы передавать отдельно от метаданных. Mac получает собственную локальную базу и device identity; копирование Android БД или content URI не является способом переноса коллекции.

Готовность: Mac и Android работают с одним аккаунтом и поддерживаемым сервером, не дублируют историю, не смешивают владельцев данных и сохраняют автономную локальную работу при отключении сети.

## Этап 6 Добавить офлайн загрузки и системное поведение

Ориентир: 3–5 рабочих дней. Владельцы: направления аудио, данных и UI по своим границам.

- Реализовать desktop download execution/index за media port. База хранит intent и coarse state; один компонент владеет прогрессом и фактическими байтами.
- Разделить управляемые скачанные файлы и вытесняемый stream cache. Pinned/user downloads не исчезают из-за обычного LRU; учитывать квоту и резерв места.
- Проверить resume/cancel, частичные файлы, заполненный диск, сетевые ошибки и целостность. Статус «доступно офлайн» выдавать только при наличии всех необходимых проверенных байтов.
- Добавить media keys, системные title/artist/artwork и play/pause/seek commands, меню приложения, поведение окна/Dock и sleep/wake. После пробуждения обновлять серверные credentials и доступность источника.
- Закрыть согласованную матрицу остальных функций Android. Для server-owned задач переиспользовать API и состояния, не вводить второй локальный владелец серверных операций.

Готовность: скачанные треки играют без сети; sleep/wake, закрытие окна, полный Quit и перезапуск имеют понятное и проверенное поведение. У каждой функции матрицы есть результат проверки либо явное исключение из релиза.

## Этап 7 Подготовить проверяемый релиз

Ориентир: 3–5 рабочих дней плюс резерв на найденные проблемы. Тестовую упаковку и macOS CI начать ещё на этапе 1.

1. Добавить macOS gate для shared/desktop tests, native smoke и упаковки. Сохранить Android gates; серверные изменения проходят contract/server/migration gates на disposable resources.
2. Проверить реальные `.app`/`.dmg` на чистой системе без установленного JDK, VLC и других случайных зависимостей. Все требуемые runtime и native libraries должны входить в пакет.
3. Выполнить подпись и нотариальное заверение для внешнего распространения, проверить запуск скачанного пакета через Gatekeeper. Секреты подписи хранить вне checkout.
4. Проверить обновление поверх предыдущей desktop-сборки с сохранением базы, библиотеки, аккаунта и загрузок. Возврат к более старому приложению не должен откатывать схему или удалять данные.
5. Пройти финальную функциональную матрицу на заявленных macOS/архитектурах: настоящий звук, media keys, внешние диски, sleep/wake, сеть, accessibility и account lifecycle.
6. Зафиксировать commit/snapshot, architecture, toolchain, hashes установщиков и native dependencies, schema versions, server compatibility, лицензии, release notes и известные ограничения.

Готовность: один конкретный пакет проходит все проверки своего заявленного объёма и обновления, а Android не получает регрессий. Обычная сборка из IDE не заменяет проверку установщика. Стандартный Compose `packageDmg` выполняется на macOS; пользовательский пакет включает Java runtime. [Документация упаковки](https://kotlinlang.org/docs/multiplatform/compose-native-distribution.html).

## Организация параллельной работы

| Рабочий поток | Владение | Зависимости |
| --- | --- | --- |
| Координатор | Исходный снимок, модульные границы, Gradle/CI, серверная совместимость, интеграция, выпуск | Порты фиксирует до параллельных изменений |
| Общий код и данные | Domain/application, Room, общие repositories, JVM transport/crypto, sync | Использует согласованные порты; аккаунт подключает после этапа 4 |
| Desktop UI | Shared components/resources, desktop shell, окна, клавиатура, продуктовые экраны | Может начать с fake adapters после фиксации API |
| Аудио и macOS | Движок, native bridge, файлы, Keychain/device signing, media controls, downloads | Реальный Mac нужен с ранней проверки |

Для независимых чатов использовать отдельные worktrees одного согласованного снимка. Новые worktrees не должны случайно стартовать без нужных незакоммиченных изменений. Не редактировать одни и те же файлы несколькими потоками. Координатор владеет build-конфигурацией, общими интерфейсами и точкой интеграции.

Объединять небольшие завершённые участки регулярно. Каждый результат включает список изменений, необходимую конфигурацию и результаты затронутых проверок. Субагентов подключать к ограниченным задачам: инвентаризации, отдельным адаптерам, анализу ошибок и независимому review. Проверки общих интерфейсов и build-конфигурации выполнять до очередного расширения объёма.

На одном хосте Gradle invocations идут последовательно, с одним worker и штатным heap из `gradle.properties`. Параллельное написание кода не отменяет это правило проекта. Учесть локальные правила разработки в `CODING_STANDARDS.md` и границы действий в `AGENTS.md`.

## Порядок зависимостей и календарный ориентир

```text
Baseline and ports
  -> audio/native spike + shared extraction + UI shell
  -> local player

Baseline and device contract review
  -> compatible server extension + Keychain/signature proof
  -> accounts and sync + Vault streaming

Local player + accounts/streaming
  -> managed downloads + system integration + feature closure
  -> exact package qualification and release
```

| Период | Основной результат |
| --- | --- |
| Первые 2–3 рабочих дня | Исходный снимок, проверка toolchain, решение по движку и системным адаптерам |
| К концу первой рабочей недели | Локальный прототип; начальная общая база и desktop UI |
| Вторая и третья недели | Постоянная библиотека, серверная совместимость, аккаунт, Vault, базовая синхронизация |
| Четвёртая неделя | Офлайн загрузки, системные интеграции, закрытие согласованной матрицы функций |
| Пятая и шестая недели | Квалификация пакетов и обновления, исправления, документация выпуска |

Плановый ориентир при одном координаторе и трёх рабочих направлениях: 4–7 рабочих дней до локального прототипа, 2–3 недели до версии для ежедневного использования, 4–6 недель до релиза согласованного объёма. Это сроки от начала, они не суммируются. Длительности отдельных этапов перекрываются и включают интеграцию.

Если аудиодвижок, versioned device contracts или Intel/native packaging требуют существенной доработки, резервный ориентир — 6–8 недель. Недоступный Mac и расширение матрицы функций меняют календарный срок. Уточнить оценку после этапов 0–1 и повторно после работающих аккаунтов/Vault.

## Обязательные проверки результата

- Чистая установка и обновление desktop не требуют отдельно установленного runtime и сохраняют данные.
- Локальные импорт, поиск, плейлист и playback работают без сервера; offline состояние проверяется с отключённой сетью.
- Очередь, позиция и listening-event identity переживают перезапуск; дубликаты треков в очереди сохраняют разные queue entry IDs.
- Shared SQL и миграции проверены на настоящем SQLite, серверные CHECK/migrations — на одноразовом PostgreSQL со старым и новым типом устройства.
- Старый Android работает с обновлённым сервером; unsupported Mac/server сочетание явно обозначается.
- Синхронизация между Android и Mac сохраняет account/device ownership, идемпотентность и неизменность уже созданных Journal events.
- Crypto/canonicalization fixtures, повреждённые recovery документы, revoked device, истёкшая сессия и неподдерживаемая платформа проверены без ослабления подписей и доверия серверу.
- HTTP seek/Range, redirect и cache/download сценарии проверены настоящим движком, а не fake UI state.
- Установка, Gatekeeper, media keys, sleep/wake и заявленные архитектуры проверены реальным пакетом на Mac.
- Финальный manifest связывает исходники, пакет, схемы, совместимый сервер и результаты проверок; реальные секреты и личные пути не попадают в общие логи и evidence.
