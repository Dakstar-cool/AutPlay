# CI repair, 2026-09-16

## Stale dependent lockfiles

The publication at `97a33cf` added the server's pinned `httpx2[socks]` and
`yt-dlp[default,pin]` dependencies. Both optional GPU projects use the server as a
local path dependency, but their independent lockfiles still described its old
requirements. `uv sync --frozen` installed those old graphs successfully, then
`uv lock --check` correctly rejected them. This stopped the GPU and training jobs
and the canonical Android host gate before its Gradle stage.

Regenerating `gpu/uv.lock` and `gpu/training/uv.lock` with the pinned uv 0.12.3
adds the required dependency closure. Training's `idna` changes from 3.19 to 3.18
to satisfy the exact version required by `yt-dlp[pin]`. Python, CUDA, PyTorch,
ONNX Runtime and application dependency pins remain unchanged. No workflow,
assertion, skip, timeout or security setting was relaxed.

For the repeated lock error, the investigated options were regenerating the
existing lockfiles, allowing sync to update them, refreshing selected packages,
or recreating the locks from scratch. Regenerating existing locks preserves
compatible versions and avoids an unrelated dependency upgrade. See the
[uv locking documentation](https://docs.astral.sh/uv/concepts/projects/sync/).

## Verification scope

- All five independent Python projects pass `uv lock --check`.
- The full Linux GPU job passes frozen synchronization, lock validation, Ruff,
  formatting, strict mypy (27 files) and all 35 tests on Python 3.14.7 / uv 0.12.3.
- The full Linux training job passes frozen synchronization, lock validation,
  Ruff, formatting (25 files), strict mypy (23 files) and all 37 tests. The five
  existing PyTorch export warnings remain visible; there are no skipped tests.
- The previous publication's Android, root, server and acquisition test results
  remain applicable to their unchanged inputs. The repair reruns the two affected
  Linux dependency environments. After publication, GitHub reruns the complete
  canonical Android gate with the corrected locks.
- No accelerator or device-acceptance claim is made by these host checks.

## Managed Dependency Graph limitation

The separate GitHub-managed `dynamic/dependabot/update-graph` run
[35117339285](https://github.com/Dakstar-cool/AutPlay/actions/runs/35117339285)
failed before dependency analysis with `tool_version_not_supported` for
`>=3.14.7,<3.15`. This is not one of the repository's test workflows.

The updater image used by that run is tagged `30797444720db27c114150b4b2d620e5ab80b6bc`.
Its [Python runtime list](https://github.com/dependabot/dependabot-core/blob/30797444720db27c114150b4b2d620e5ab80b6bc/python/lib/dependabot/python/language.rb)
offers Python 3.14.5 as its newest 3.14 runtime. Its
[version selection](https://github.com/dependabot/dependabot-core/blob/30797444720db27c114150b4b2d620e5ab80b6bc/python/lib/dependabot/python/language_version_manager.rb)
cannot satisfy the project's minimum 3.14.7. The uv parser prioritizes
`pyproject.toml` over `.python-version`, so adding another version file would not
repair that incompatibility.

Resolution requires a compatible runtime in GitHub's managed updater image.
The project retains its pinned Python version and enabled dependency graph;
this report does not claim that the managed graph job has been repaired.
Related upstream report:
[dependabot-core#14883](https://github.com/dependabot/dependabot-core/issues/14883).
