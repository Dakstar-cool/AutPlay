# CI repair, 2026-09-14

The first checks for PR #6 exposed runner setup differences from the validated
acquisition container. The acquisition job lacked ffmpeg/ffprobe, causing six
test failures and thirteen fixture errors. CI now installs the same immutable
`mwader/static-ffmpeg:8.1.2` image binaries as the acquisition runtime. A temporary
container is created only for copying files, never started, and removed on exit.
Both tool versions are checked before exporting their directory to `GITHUB_PATH`.
The Android host and release workflows also install them because their shared
`scripts/check.sh` runs acquisition tests.

The server gate failed Ruff import ordering in two new/changed test modules.
Their imports now follow the existing explicit root-invocation configuration.
The connected Android workflow used `sdkmanager` without a PATH entry; it now
resolves and checks the executable under the hosted Android SDK. The initial
Android host run at `56538fe` was explicitly cancelled by the operator during dependency
downloads; that log contains no Android code/test failure.

## Repeated-error investigation

For missing media executables, the alternatives were an OS package install,
a checksum-verified archive, building from source, moving all tests into Docker,
or extracting the already-pinned runtime tools. The last option preserves the
existing media version and exercises the normal host test command. References:
[static-ffmpeg upstream](https://github.com/wader/static-ffmpeg),
[Docker copy semantics](https://docs.docker.com/reference/cli/docker/container/cp/),
[GitHub PATH export](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-commands#adding-a-system-path).

For the reproduced Ruff errors, the alternatives were changing the invocation
working directory, adding explicit source paths, classifying the whole package
as first-party, or aligning the two inconsistent imports. The last option fixes
the failing files without reformatting unrelated server modules. Ruff documents
that explicit `--config` resolves relative paths from the invocation directory:
[configuration discovery](https://docs.astral.sh/ruff/configuration/#config-file-discovery).

## Connected Android follow-up

After the SDK setup repair, API 26 completed 212 tests and exposed five failures.
Four UI scenarios assumed that controls below the viewport could be clicked or
asserted visible without scrolling. They now scroll existing containers and keep
their visibility, confirmation, callback, and disabled-control assertions. The
local reproduction uses API 26 at the CI viewport of 320 by 640 with density 160;
it reproduced all four UI failures before these changes.

The playback restoration test could accept a placeholder position before the
real media source was ready. Its assertion now requires readiness and the saved
position together, retaining its existing timeout, session identity, played-time,
main-thread responsiveness, and subsequent checkpoint checks.

With the stronger test and the old app APK, all four UI scenarios passed while
restoration failed at the original ten-second deadline. Media3 replaces the
placeholder's period when the real source arrives and chooses its default
position. The service now captures the current position inside the existing
generation/entry checks and restores it immediately after replacement. Resolving
the next queue entry does not seek the current player. This uses the latest
player position, preserving a seek made while resolution was pending.

For this reproduced timeout, the alternatives were a longer test deadline,
waiting for all sources before restoring, implementing an updateable placeholder
source, or preserving the position when replacing the current source. The last
option fixes the observed reset locally without blocking current playback on the
next lookup. The pinned
[Media3 1.10.1 replacement implementation](https://github.com/androidx/media/blob/1.10.1/libraries/exoplayer/src/main/java/androidx/media3/exoplayer/ExoPlayerImpl.java)
explains why a changed period resets the position.

The UI investigation considered explicit scrolling, changing the emulator size,
checking only semantics existence, and bypassing pointer input with semantic
callbacks. Scrolling preserves the user interaction and tests the existing layout
at the failing viewport. See the Android documentation for
[Compose test actions and assertions](https://developer.android.com/develop/ui/compose/testing/apis).
The emulator location was resolved through the configured SDK environment
variables, rather than guessing the default home directory; the alternatives
were listing SDK AVDs, inspecting environment overrides, scanning directories,
or creating a new disposable AVD. A read-only overlay of an existing API 26 AVD
keeps the saved device state intact. See
[Android environment variables](https://developer.android.com/tools/variables).

The full local suite also exposed an offscreen account-confirmation button;
that test now mounts the panel in a scroll container, as the production route
does, and scrolls before its existing callback assertion. The invitation scenario
now starts before creation and feeds callback results back into observable test
state: Create opens the secret dialog, and Cancel removes it. Its modal assertions
use the dialog directly; only the underlying Create button needs scrolling.
This preserves a real create/cancel flow instead of clicking behind an already
open dialog or bypassing pointer input with semantics callbacks. WorkManager
timeouts were traced to airplane mode inherited from the saved local AVD:
JobScheduler reported unsatisfied CONNECTIVITY and no active default network.
The alternatives were restoring the disposable emulator's network, creating a
fresh AVD, replacing the real scheduler with TestDriver, or relaxing network
constraints/timeouts. The saved AVD returned to airplane mode during recovery,
so final validation uses a fresh disposable AVD with the CI default profile:
API 26, x86_64/default image, 320 by 640, density 160, disabled animations,
and a validated active network. This retains real scheduling coverage. Worker
code and timeouts remain unchanged. References:
[emulator network controls](https://developer.android.com/studio/run/emulator-console),
[WorkManager constraint simulation](https://developer.android.com/develop/background-work/background-tasks/testing/persistent/integration-testing).

## Resolution cancellation follow-up

The next published connected run exposed a timing-dependent crash despite the
local 212-test pass: cancelling source-resolution jobs during queue replacement
could synchronously run completion handlers that removed entries from the same
map being iterated. The obsolete host build was cancelled after this failure.

The cancellation helper now detaches the old jobs and clears their registry
before cancelling them. Both queue replacement and service shutdown use it;
completion callbacks retain their job-identity guard. Two deterministic JVM
tests exercise inline self-removal and registration of a replacement job during
completion. Both failed against the original cancellation order, including the
same `ConcurrentModificationException` seen in CI.

The investigation considered a detached snapshot, iterator-based removal,
deferring completion cleanup, and a concurrent map. Detaching the old generation
is the smallest fix within the existing player-looper ownership; unlike a live
iterator or final `clear()`, it cannot discard newly registered jobs. See the
[coroutine completion contract](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-job/invoke-on-completion.html)
and [JDK fail-fast iteration contract](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/util/LinkedHashMap.html).

The fixed code passed the complete local Android gate in 13 minutes 6 seconds:
lint, all 279 JVM tests with zero failures/errors/skips, and debug, trustedLan,
release and instrumentation APK assembly. The clean API 26 runner then reported
`OK (212 tests)` in 218.020 seconds, including the previously crashing queue
replacement scenario. The general runner has three existing harness-gated
assumptions: the two process-death stages are executed by their separate script;
the joined M5B end-to-end scenario requires its own server harness and is outside
this connected workflow. The 212 count includes these three assumptions.
Both process-death stages also passed on the same APKs with a verified live
process/force-stop boundary. APK hashes remained unchanged across the checks.
The final four-file diff passed a bounded read-only review and whitespace checks.
